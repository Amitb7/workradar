WorkRadar — Product Requirements Document

AI-powered work prioritisation dashboard for managers
Author: Amit Butola · Version 1.0 (MVP) · 16 Oct 2026
Status: MVP built on mock data

1. Problem statement

Managers cannot see what matters today without opening four tools. An engineering manager's work signals are scattered across Slack (requests, incidents, mentions), Jira (tickets, deadlines, blocked status), GitHub (reviews, failing CI) and Email (escalations, leadership asks). Each tool ranks by recency, not importance, and none of them shows who is blocked on whom. The result: the first 30–60 minutes of the day go into tab-hopping and mental triage, urgent items surface late, and teammates stay blocked longer than necessary.

WorkRadar consolidates these signals into one explainable, ranked view that answers four questions in under three minutes: What is my top work today? What happened today? What needs immediate attention? Who is blocked?

2. Target users

  • Primary: Engineering managers / team leads running 5–12 people across Slack, Jira, GitHub and Email.
  • Secondary: Product managers and tech leads who coordinate releases and unblock cross-functional work.
  • Later: Directors needing a multi-team roll-up (out of MVP scope).

5. Key pain points

  1. Fragmentation — 4+ tools, 4 inboxes, no single priority order.
  2. Noise over signal — FYIs and bot messages look as loud as incidents.
  3. Invisible blockers — "waiting on X" lives in DMs; managers learn days late.
  4. Stale asks on the manager — PR reviews and approvals age silently and block the team.
  5. No "why" — existing AI summaries are opaque, so managers don't trust them.
  6. Unowned work — high-severity items with no assignee fall through the cracks.

7. MVP scope

In scope (built)

  • Unified WorkItem model normalising Slack, Jira, GitHub and Email (26 realistic mock items, timestamps relative to "now").
  • Explainable priority engine: 0–100 score from severity, due date, mentions/review requests, blockers, blocked duration, unblocking value, customer impact, ownership gaps; tiers P0–P3; every point carries a reason.
  • AI daily brief: Top work · Needs attention · Who is blocked · What happened. Deterministic rules engine by default; optional LLM regeneration with JSON schema + ID validation and automatic fallback.
  • Dashboard, Priority Feed (views + filters), Item Details (score breakdown, next step, related items), Search (operators, highlights).
  • Actions: Assign (suggested owner), Mark Done / Reopen, Snooze / Unsnooze — with toast + Undo, persisted locally.
  • Empty / error states: no results, filters empty, partial source failure banner, all-sources failure with retry, item not found, loading skeletons.
  • Responsive (phone → desktop), dark mode, keyboard "/" to search.

Out of scope (MVP)

  • Real OAuth connectors and live ingestion (mock data per brief).
  • Write-back to source tools (actions are local in MVP).
  • Multi-team / director roll-up, role-based access.
  • Push / Slack DM notifications, scheduled email digests.
  • Learned (ML) personalisation of weights.

Key product decisions

  • Explainability over magic: ranking is rules-based and transparent; the LLM only summarises a pre-ranked list, so it cannot invent priorities.
  • Graceful degradation: one source failing never blanks the app; the user is told which data is missing.
  • Actions in-place: Assign/Snooze/Done on every card to cut clicks; Undo instead of confirm dialogs.
  • Privacy-first default: no data leaves the browser unless the user adds an LLM key.

8. Assumptions

  • Slack, Jira, GitHub and Email together hold the large majority of a manager's actionable work signals.
  • Managers will trust and act on a ranked list if each item shows why it is ranked.
  • Severity, due date, direct asks and blockers are reliable proxies for urgency in the first version.
  • "Blocked" can be detected from Jira status, labels and phrases like "waiting on / blocked by" in messages.
  • Read-only access is acceptable to security teams for v1; write-back comes later.
  • Mock data is representative of a 6-person payments team on a release day.
  • An LLM is helpful for tone and synthesis but not required for correctness.
  • Users work primarily on desktop in the morning and check in on mobile later.

10. Risks & mitigations

Wrong ranking erodes trust → visible reasons, one-click override, feedback loop in v2 · LLM hallucination → LLM only summarises pre-ranked items, output IDs validated, deterministic fallback · Privacy → read-only scopes, local-first, LLM opt-in · Connector outages → per-source sync status and partial-results banner.
