2. Significant prompts

P1 — Framing. "Act as an expert Product Manager. I need to build WorkRadar, an AI-powered web application that consolidates work priorities from Slack, Jira, GitHub and Email for managers… guide me through the six-step process: PRD (max 2 pages), high-fidelity UI designs, functional MVP with Assign / Mark Done / Snooze, AI Workflow document, 5–7 min demo plan, final deliverables."
P2 — Decisions. Chose: build everything in one pass · React + Vite · "Rule-based summary + optional LLM" (so the demo works offline and the LLM can't invent priorities).
P3 — Data model & scoring (internal design step). "Normalise all four sources into one WorkItem shape. Score 0–100 with every point paired to a human-readable reason; tiers P0–P3. Mock data for a 6-person payments team on a release day, timestamps relative to now, including an incident, a stale PR review, blocked teammates, an unassigned customer escalation, FYIs, and items already done today."
P4 — LLM brief prompt (shipped in src/lib/summary.js). "You are WorkRadar, an assistant for an engineering manager… Write her daily brief from the JSON below. Be concrete, cite refs, no fluff, no invented facts. Return ONLY valid JSON with keys headline, topWork (max 3, items she owns that are NOT in attention), happened, attention (only truly urgent), blocked. Use only ids that appear in the input."
P5 — Review loop. After each build: "Screenshot every screen and state, look at them, and fix anything that looks wrong or reads poorly." This produced the fixes listed in section 4.

3. What AI generated

  • PRD — problem statement, personas (Neha, Rahul, Meera), before/after journey, metrics, scope, assumptions, must/nice feature table; condensed to two pages.
  • Application code (~2,200 lines): store with undoable actions and local persistence, hash router, priority engine, search with operators, rules-based + LLM brief, 5 pages, shared components, CSS design system with dark mode and phone layout.
  • Mock data — 26 realistic cross-tool items with threads, blockers and relations.
  • Unit tests — 7 Vitest tests (scores equal the sum of reasons, ranking sanity, blocked grouping, brief sections, search operators).
  • UX design file, screenshots, this document and the demo script.

5. Key trade-offs

DecisionChosenTrade-off
How to rankTransparent rules engine (weights in code), not an LLM+ explainable, testable, instant, free. − weights are hand-tuned; needs a feedback loop to personalise.
How to summariseRules-based brief by default, optional LLM over the already-ranked list with JSON + ID validation+ no hallucinated items, works offline. − rule text is less fluent than an LLM.
DataMock data, relative timestamps+ demo always looks like "today", no OAuth setup. − real-world messiness (duplicates, noisy bots) not exercised.
LLM call locationDirectly from the browser with the user's own key+ no backend needed for the MVP. − not production-safe; production would proxy through a server.
ActionsLocal state + Undo toast, persisted in localStorage+ fast, no confirm dialogs. − does not write back to Jira/Slack yet.
Design processCode-first: screens designed in the browser, then captured into the design file+ design and product never drift; real states. − less room for wide early exploration than a Figma-first flow.
Routing / depsTiny hash router, one icon library+ small bundle (≈68 KB gzip), deep links work on any static host. − fewer router features.

6. Where AI helped most / least

  • Most: scaffolding the whole app and states quickly; generating believable cross-tool mock data; catching its own visual bugs from screenshots.
  • Least: product judgement — e.g. the first brief duplicated sections and under-ranked "unblocking" work; these needed a PM's review against the user's actual questions.
